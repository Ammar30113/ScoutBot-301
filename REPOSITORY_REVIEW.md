## Original audit snapshot

Reviewed September 7, 2026. Source commit: `334c94d5be0ad665dba6e36aa3fc7ae333a3aa91`.

**Decision: useful research scaffolding, unsuitable for unattended real-money trading today.** Alpaca eligibility is one blocker; execution correctness, trustworthy simulation, and portfolio isolation are more consequential. No profitable trading edge has been established by the evidence available in this review.

For an owner working 9–5, earning approximately CAD 60,000 annually, and already holding long-term investments in Wealthsimple TFSA/RRSP accounts, the recommended first product is a daily investment monitor and paper strategy runner. Keep the long-term portfolio outside the experimental execution system. Consider real-money execution only after the gates below pass.

**Scope and verification**

- Inspected all 70 tracked files: 56 Python files, three universe CSVs, documentation, configuration, dependency declarations, CI, and deployment files. The large Russell CSV was inspected for structure and candidate-selection behavior; its individual constituents were not independently validated against current exchange listings.
- Local tests: `62 passed` on Python 3.12 in an isolated temporary environment, using actual installed dependencies. `ruff check .` passed. CI targets Python 3.11.
- GitHub CI at the reviewed commit is successful: [CI run](https://github.com/Ammar30113/ScoutBot-301/actions/runs/25577405497).
- GitHub records a successful Railway deployment status dated July 26, 2026, for this commit. This is historical deployment evidence, not proof of a running worker, valid credentials, persistent storage, or successful trading today.
- Local preflight fails because trading credentials and market-data providers are not configured. No brokerage was connected, no trading worker was started, and no orders were placed.
- Executed isolated, mocked reproductions of the main-loop, order lifecycle, configuration, model startup, and simulator failures below. These validate program behavior, not exchange behavior or profitability.
- No committed trained model, historical OHLCV dataset, strategy evaluation report, or fill-based performance record was available. Hosted configuration, current Railway logs, account permissions, and live broker fills remain unverified.
- At the time of this original audit, only documentation had changed. The implementation update above supersedes that statement for the current working tree.

**Existing architecture worth retaining**

`main.py` runs a synchronous loop every 900 seconds. It reads account P&L and SPY crash data, builds a universe, routes ORB/momentum/reversal signals with a daily swing fallback, allocates capital, submits Alpaca bracket orders, reconciles pending entries, and evaluates exits. Market data flows through Alpaca, TwelveData, AlphaVantage, and Marketstack adapters. State uses local JSON and JSONL files. The backtester patches global routers to replay CSV bars through some strategy and risk code.

The module boundaries, explicit live-trading opt-in, risk sizing, provider timeouts, cache limits, and test infrastructure are useful. Preserve them while introducing a shared clock, typed broker interface, explicit strategy selection, and durable order ledger. A rewrite into microservices would add complexity without resolving the underlying defects.

**Findings, ordered by consequence**

1. **P0 — Existing investments have no ownership protection.** `main.py:184–232` evaluates every broker position, including positions the bot did not create. `trader/risk_model.py:109–137` applies profit/stop thresholds before checking whether an entry timestamp exists. An old long-term holding up more than the default 1.8% can therefore receive an exit instruction when the loop reaches this stage. Add account allowlisting and ownership by account, strategy, instrument, and confirmed fill. Prefer a separate experimental account. Never infer permission to manage a holding from its presence in the broker response.

2. **P0 — No-entry paths skip reconciliation and exits.** `main.py:84–115` continues on missing required crash data, an empty universe, or no signals. Management starts only at line 184. All three branches reproduced zero reconciliation calls and zero position-management calls. Move management ahead of scanning and isolate it from signal/provider failures. Broker-held stops help, but do not repair skipped time stops or reconciliation.

3. **P0 — Duplicate pending orders can be submitted.** `trader/execution_adapter.py:293–300` checks filled positions, not open entry orders. `_pending_entries` is memory-only, not used to reserve capacity, and expires locally without cancelling the broker order. Two identical signals against an account with no filled positions reproduced two accepted submissions. Introduce a persisted order intent with a stable client ID, reserve cash/slots, inspect open orders, and reconcile ambiguous timeouts before retrying. Recovery must work after process restart and partial fills.

4. **P0 — Exit submission is treated as completion.** `trader/execution_adapter.py:537–552` clears ownership metadata and logs `closed` immediately after submitting a close, without waiting for a fill. A mocked unfilled close reproduced this. Bracket-child cancellation/replacement is absent; positions held for orders can be skipped or produce quantity errors. Track closing orders to terminal status and reconcile protective children. Broker-triggered exits need the same fill ledger. Do not calculate realized P&L from a pre-submission quote.

5. **P1 — The budget is replenished each cycle, not a hard capital allocation.** `trader/allocation.py:35–41` resets the budget on every call. Individual notional limits and per-trade stop-risk sizing exist, but total open exposure plus pending orders is not bounded by a dedicated bot capital ledger. Sizing uses whole-account equity and buying power, potentially including margin or unrelated savings. Add an explicit capital allocation in the correct currency, settled cash, reserved cash, gross exposure, portfolio stop risk, turnover, and cumulative drawdown limits. A daily loss limit does not guarantee a maximum loss through gaps.

6. **P1 — Account failures and state loss weaken controls.** A P&L fetch failure returns `None`, while `main.py` initializes trading as allowed. `list_positions()` returns `[]` on API errors, which can cause synchronization to erase entry metadata. JSON writes are non-atomic; unreadable state becomes a fresh empty state, potentially resetting the daily-loss baseline. Use transactional persistence, distinguish unavailable from empty, and block new entries when balances/order state cannot be established. Persist a loss-limit latch until an explicit reset policy permits trading again.

7. **P1 — Alpaca bar requests do not request the intended history.** `data/alpaca_provider.py:89–98` sends timeframe and limit without start/end, descending sort, or pagination. Alpaca defaults to the current day's beginning and ascending order. Thus a limit does not mean the latest N bars or N days. This can produce old intraday bars and insufficient daily history. Request explicit periods, paginate, normalize and sort, and assert the requested coverage. [Alpaca single-symbol bars](https://docs.alpaca.markets/us/reference/stockbarsingle-1).

8. **P1 — Intraday history is too short for the configured indicators.** The 120-minute request produces approximately 24–25 five-minute bars. Default MACD needs 26 observations for its line and about 34 for its signal/histogram. A 120-bar one-minute fixture produced 24 five-minute bars, NaN MACD values, and a failed entry filter. Training uses a longer window, so inference has different warm-up characteristics. Request sufficient completed bars and reject incomplete feature vectors explicitly. Also use exchange-session VWAP rather than an arbitrary rolling-window cumulative VWAP.

9. **P1 — Five-minute logic is polled on a fifteen-minute cadence.** Scheduler interval, cache TTL, and permitted intraday staleness default to 900 seconds. Resampling does not exclude the unfinished five-minute bucket. A scalar execution price carries no timestamp, bid/ask spread, or currency. Add closed-bar semantics and fresh executable quotes. For the recommended daily strategy, use completed daily data with session-aware availability and separate quote requirements at execution.

10. **P1 — The backtest clock is not simulated consistently.** `trader/risk_model.py:146` uses wall-clock time; ORB uses today's date/session. A position opened at a historical timestamp was immediately eligible for a time exit at an unchanged price. Inject simulation time into all strategy, risk, cache, logging, and session decisions; never run historical decisions against the real clock.

11. **P1 — The simulator corrupts holdings on repeat buys.** `backtest/sim_broker.py:73–93` subtracts cash and overwrites the position keyed by symbol. Starting with 1,000 and buying one 100-priced share twice produced cash 800, one recorded share, and equity 900. Reject duplicate entries to match live behavior, or explicitly aggregate shares/cost basis if scaling is supported. Test conservation of equity and cash.

12. **P1 — Backtesting diverges from execution.** `backtest/runner.py` omits the live risk-sizing step and signal-specific stop, target, and hold metadata; it uses close-price exits instead of realistic bracket execution, and defaults to zero slippage and fees. Same-bar signal/fill timing needs explicit availability rules. `BacktestPriceRouter.bars_age_seconds()` expects numeric timestamps but receives pandas timestamps after resampling; the reproduction returned no age. Global monkey-patching is not restored. Build a deterministic offline runner that cannot call live services or train on future data, shares execution constraints, models next-eligible fills, and reports actual modeled costs. Include dividends, splits, delistings/universe history where relevant, and CAD/USD effects.

13. **P1 — ML startup does not honor the documented switch.** With a missing model, `_load_or_train_model()` calls `_train_model()` even when `TRAIN_ML_ON_STARTUP=false`; the flag only guards a path for an invalid existing artifact. Mocking training reproduced one training call and one persistence attempt with the flag false. Fix the branch; production should load only an explicitly approved model or use an explicitly selected non-ML strategy.

14. **P1 — ML probabilities are not evidence of an edge.** Training uses a short recent sample from ten mostly large-cap symbols, while the intended universe is small caps. There is no chronological holdout, walk-forward evaluation, calibration, cost-aware target, or model provenance. The final unknown next-bar label becomes zero because the comparison converts NaN to false before dropping missing data. The prediction path raises scores using a heuristic floor and scales features only during crash inference. These outputs should not be interpreted as calibrated win probabilities. Validate a rules-only baseline before adding ML.

15. **P1 — Strategy fallbacks silently change risk.** Stale SPY data or no intraday signals can activate swing trading. Swing holds for up to 24 hours but shares DAY bracket orders with intraday strategies; overnight protection is not established. Crash mode allows new long entries and relaxes technical filters rather than simply pausing. The reversal router accepts any nonzero reversal score, including bearish values, while `main.py` always emits BUY. Make strategy and overnight permissions explicit, handle direction, and default a market/data emergency to no new exposure. No signal should be a normal successful outcome.

16. **P1 — Filtering can fail open.** `universe/universe_builder.py:282–300` can return unfiltered fallback symbols after all filters reject candidates; the setting defaults true. The fallback contains ETFs/large caps unlike the advertised small-cap universe. Candidate truncation also takes the first 500 symbols of an alphabetically ordered CSV before liquidity ranking. Disable unfiltered fallback for execution, maintain a versioned allowlist, refresh symbol tradability, and compute the universe outside the position-management loop.

17. **P1 — The trade journal is incomplete with real SDK types.** Alpaca's installed `Order.id` is a UUID; `json.dumps` in `trader/trade_logger.py` does not serialize it. A UUID submission event reproduced a zero-byte log and a serialization warning. Alpaca status enums stringify as `OrderStatus.FILLED`, not the plain strings used in reconciliation comparisons. Normalize broker identifiers/statuses at the adapter boundary. The installed account model also lacks `realized_pl`, so the P&L tracker's fallback zero is not a realized trading ledger. Derive realized results from fills and fees.

18. **P1 — Configuration validation is incomplete and not a startup gate.** NaN values for budget and loss/risk percentages passed preflight in isolation. Numeric parsing does not establish finite values or valid ranges; `main.py` does not run preflight. Validate all financial inputs and mode/account consistency before starting. Keep paper/live and account identifiers unambiguous. Do not merely remove the current preflight prohibition on live trading before safety gates exist.

19. **P1 — One data adapter uses plaintext HTTP.** `data/marketstack_provider.py` sends the access key and receives pricing through an `http://` endpoint. Use a supported HTTPS endpoint and verified data entitlement. Redact API-key query parameters from exceptions/logs. Other providers use differing adjustment and timestamp conventions; normalize these before mixing histories.

20. **P2 — Sentiment and deployment add complexity without established benefit.** With Twitter disabled by default, GPT is asked for sentiment without supplied current news or a retrieval tool. Neutral/unavailable sentiment becomes a positive 0.5 component after normalization. Twitter consumes scarce quota before ticker matching and does not retain a shared, time-validated news corpus. Disable both for initial strategy validation. The repo has no durable database, external heartbeat, alert delivery, worker ownership lock, end-to-end recovery tests, or dependency lock. Docker/Procfile packaging and historical deployment success do not establish these capabilities.

**Strategy, capital, and income expectations**

The first objective should be trustworthy automation and capital preservation. Running daily does not require trading daily. Keep normal retirement/long-term investing intact. Wealthsimple's recurring purchases and dividend reinvestment already provide basic investing automation without this bot. [Recurring purchases](https://help.wealthsimple.com/hc/en-ca/articles/9544942923547-Set-up-a-recurring-investment), [dividend reinvestment](https://help.wealthsimple.com/hc/en-ca/articles/15755618952347-Learn-about-dividend-reinvestments-on-Wealthsimple).

For the experimental strategy, research one transparent, long-only daily ETF trend model with a small liquid unleveraged universe, a fixed weekly decision schedule, explicit cash allocation, and no automatic switch to another strategy. A predeclared hypothesis could compare 6–12-month momentum with a long-term trend filter; this is a hypothesis to test, not an established profitable strategy or a prescription to buy particular ETFs. Compare it against buy-and-hold and a contribution-aware rebalance baseline under the same cash flows, costs, currency, and exposure. Adapt instrument choice to verified broker marketplace permissions.

Defer small-cap ORB, crash dip-buying, short selling, leverage, options-income strategies, and AI-directed discretionary orders. They add execution, monitoring, or tail risk before the system has reliable accounting. Using a daily signal still requires broker-held protection where appropriate and active monitoring of open orders; a five-minute after-work check cannot fix an unmanaged intraday position.

Start with **zero live capital** and a **CAD 1,000-equivalent paper account**. After correctness and strategy gates pass, consider at most **CAD 500–1,000 of genuinely disposable new savings** for a supervised execution experiment, only if an emergency reserve, expensive debt, and regular savings needs are already covered. That is a conditional experiment ceiling, not an affordability conclusion from salary. Do not withdraw retirement holdings to fund it. If trade sizes and fees make conservative risk limits impractical, remain in paper mode.

Candidate paper/pilot controls: no borrowing, at most two positions, at most 50% total gross exposure, maximum modeled stop risk 0.25% of allocated bot equity per trade, no new entries after a 1% daily loss, and a persistent halt at 5% cumulative drawdown until review. These are engineering starting limits to evaluate, not guarantees: gaps and outages can exceed planned stop risk. Include fees when deciding whether a trade is viable; never force a one-share trade that violates the risk budget.

Do not treat TFSA and RRSP as interchangeable active-trading accounts. CRA states TFSA business income can be taxable and determines business activity from the facts. Its technical guidance distinguishes RRSP/RRIF treatment for qualified investments. A separate non-registered pilot simplifies ownership and keeps the experiment apart from long-term registered savings, while still requiring proper tax records. [CRA registered-plan business rules](https://www.canada.ca/en/revenue-agency/services/tax/technical-information/income-tax/income-tax-folios-index/series-3-property-investments-savings-plans/series-3-property-investments-savings-plan-folio-10-registered-plans-individuals/income-tax-folio-s3-f10-c1-qualified-investments-rrsps-resps-rrifs-rdsps-tfsas.html).

Wealthsimple charges 1.5% FX on each U.S.-listed purchase/sale from a CAD account; a round trip therefore costs roughly 3% in conversion friction at an unchanged exchange rate, before market spread. This is larger than the bot's default 1.8% gross take-profit. A USD account avoids per-trade conversion but can have subscription/funding costs. Build currency-aware accounting before considering U.S. turnover. [Wealthsimple fee schedule](https://www.wealthsimple.com/en-ca/legal/fees/trade).

Illustrative arithmetic only, not a forecast: at a hypothetical 5% annual net return, CAD 1,000 generates CAD 50/year; CAD 10,000 generates CAD 500/year; CAD 30,000 generates CAD 1,500/year. CAD 500/month would require CAD 120,000 at that assumed rate. Returns are irregular, may be negative, and are not a guaranteed withdrawal rate or cash distribution. A small pilot cannot credibly support a regular income expectation. Even a CAD 20/month operating bill consumes 24% of a CAD 1,000 account annually; this is a budget example, not a hosting quote. A reasonable initial operating-spend ceiling is CAD 0–20/month, without premium news/AI services.

**Implementation sequence and acceptance gates**

1. **Make the existing engine safe before connecting accounts.** Address ownership, unconditional position management, stable order IDs, pending reservations, fill-confirmed exits, finite configuration validation, and persistent loss limits. Add broker-failure, restart, partial-fill, and duplicate-submission tests. Preserve strategy code until execution behavior is understood.
2. **Separate broker, clock, strategy, and storage dependencies.** Introduce a small typed broker contract for account/currency, tradability, quotes, positions, open orders, submission/cancellation, and fills. Include capability flags for native stops/brackets, fractional orders, and allowed markets. Retain the Alpaca adapter; add one selected adapter later. Use a single-worker transactional SQLite store on durable storage initially, with versioned schema and backups. State must be scoped by broker account and strategy.
3. **Ship the daily read-only product.** Import a holdings snapshot manually or through a verified read-only connection. Provide data freshness, account/strategy identity, holdings overlap, CAD/USD exposure, drift, proposed trades, reasons for no trades, daily P&L, and benchmark comparison. Add an external heartbeat and connection/error alerts. Default experimental execution away from TFSA/RRSP. No public dashboard is necessary; a concise local report is enough initially.
4. **Repair and validate simulation.** Shared injected time; no live API access; explicit bar-close availability; realistic fill ordering; cash and position conservation; exact strategy metadata; commissions, spreads, FX, and dividends; historical universe where needed. Produce a reproducible command and versioned dataset/config/result manifest. A strategy fails promotion if results depend on one period, fragile parameter tuning, or optimistic transaction costs.
5. **Run daily shadow/paper operation for at least 8–12 weeks.** This tests operations, not long-run profitability. A low-turnover strategy also needs several years of out-of-sample historical evaluation spanning different conditions; a few profitable paper trades are insufficient. Require zero unexplained positions, reconciled fills/fees, successful restart and outage drills, and a transparent comparison to passive alternatives. Keep losing results and no-trade days in the record.
6. **Validate the chosen broker connection, then pilot cautiously.** Given the Wealthsimple preference, investigate SnapTrade Personal first in read-only mode. Verify self-directed account access, Personal trading permissions, allowed instruments, limit/stop/OCO support, cancellation/partial-fill behavior, reconnection, data timestamps, and provider automation rules. If it cannot support the chosen strategy safely, retain read-only Wealthsimple and use direct IBKR for a separate eligible U.S.-listed strategy. Only after these checks and explicit real-money authorization should a funded pilot be considered.

The smallest useful next deliverable is a safe daily paper/report mode plus the execution and simulator fixes. A broker swap alone would preserve the defects identified here.
